# Chef Bee — 主厨（大阶段 + 菜谱级 task）

> *从头脑风暴到菜谱级执行方案。先过饱和，再执行。*

---

## 一、Chef Bee 的双重角色

| 角色 | 消费者 | 产品 | 阶段 | 触发 |
|------|--------|------|------|------|
| **行动计划生成器** | 执行者（Worker Bee / 人） | `PLAN.md` | 启动 | 有 GOAL.md |
| **交付触发器** | 创作者（正在做事的人） | 交付决策 | 执行中 | 边际收益趋零 |

---

## 二、信息素文件体系

```
~/.worker-bee/pm/<project>/
├── GOAL.md                  ← 头脑风暴（人类写，自由格式）
├── PLAN.md                  ← 行动计划（Chef Bee 生成，LOCKED 后只读）
├── PLAN.lock                ← 决策锁（fcntl 排他锁）
├── state.json               ← 执行状态追踪（每个 task 的当前阶段）
├── _internal/
│   ├── 01-goal-parsed.md    ← 中间产物：结构化目标摘要
│   ├── 02-irreducibles.md   ← 中间产物：不可约分环节清单
│   ├── 03-tasks-raw.md      ← 中间产物：task 骨架列表
│   ├── 04-recipes.md        ← 中间产物：完整 8 字段 task
│   ├── 05-deps.md           ← 中间产物：依赖图
│   ├── 06-resources.md      ← 中间产物：资源估算
│   └── 07-contingency.md    ← 中间产物：容错矩阵
└── delivery/
    ├── diffs/               ← 版本 diff 记录
    ├── state.json           ← 交付状态追踪
    └── follow-ups.md        ← 跟进清单
```

### [1] goal-parse — 解析目标文件

| 字段 | 内容 |
|------|------|
| **消费者** | [2] irreducible-extract（内部下游） |
| **产品** | `_internal/01-goal-parsed.md` |
| **Input** | `GOAL.md` — 自由格式，人写的头脑风暴 |
| **Output** | 结构化目标摘要，精确到可枚举的列表 |
| **工具** | `fs_read_file` |
| **时间** | 5-10min（纯规则，不调 LLM） |

**GOAL.md 输入格式规范**（人写的时候尽量按这个结构）:

```markdown
# 目标: <一句话>

## 为什么做
- 原因1
- 原因2

## 已知约束
- 时间: 2周 / 无限期 / 年底前
- 预算: ￥X / 无预算
- 人员: [自己], [可联系的人A]
- 平台: [飞书], [GitHub]
- 法规: [公司法], [无特殊法规]

## 已有线索
- 线索1: 具体描述 + 来源
- 线索2: 具体描述 + 来源

## 不确定项
- 不确定1: 具体是什么不确定
- 不确定2: 具体是什么不确定

## 理想结果
- 可验证的最终交付物描述
```

**Output 格式** (`01-goal-parsed.md`):

```markdown
# 结构化目标摘要

## 目标
<一句话，从 GOAL 提取>

## 目标类型
- 主类型: [注册/采购/写作/调研/部署/谈判/创作/...]
- 子类型: [公司注册/商标注册/...]
- 复杂度: [简单(≤5步)/中等(6-15步)/复杂(>15步)]

## 约束清单（全枚举）
1. 时间约束: <有/无> — <具体内容>
2. 预算约束: <有/无> — <具体内容>
3. 人员约束: [自己], [可联系的外部人A: 角色-联系方式]
4. 平台约束: [飞书], [GitHub], [微信]
5. 法规约束: [公司法第X条], [无]
6. 地理约束: [北京], [不限]

## 资源清单（全枚举）
- 人员: N 人
- 资金: ￥X
- 工具: [工具1], [工具2]
- 信息源: [URL1], [URL2]

## 不确定项清单（全枚举）
1. Q1: <具体不确定内容> — 影响: [高/中/低] — 缓解: <如何消除不确定>
2. Q2: ...

## 线索清单（全枚举）
1. 线索1: <内容> — 来源: <URL/人/文件> — 可信度: [高/中/低]
2. 线索2: ...
```

### [2] irreducible-extract — 提取不可约分环节

| 字段 | 内容 |
|------|------|
| **消费者** | [3] task-decompose（内部下游） |
| **产品** | `_internal/02-irreducibles.md` |
| **Input** | `01-goal-parsed.md` |
| **Output** | 不可约分环节清单，每个环节标注"为什么不能省略" |
| **工具** | `fs_read_file`，可选 LLM 辅助判断 |
| **时间** | 10-15min |

**核心逻辑**:
对目标类型做模式匹配，列出该类型**必然存在**的最小步骤。然后对每个步骤做**移除测试**: 去掉它，目标还成立吗？No → 确认为不可约分。

**Output 格式** (`02-irreducibles.md`):

```markdown
# 不可约分环节清单

## 环节列表（按执行顺序）

### I-001: 查阅法规
- 为什么不可约分: 注册公司必须符合公司法，不知道法规就无法填表
- 移除测试: ❌ 去掉后无法合法注册
- 依赖: 无
- 可并行: I-002

### I-002: 联系监管部门确认执行口径
- 为什么不可约分: 各地执行口径可能与法规不同，不确认可能导致申请被拒
- 移除测试: ❌ 去掉后风险不可控
- 依赖: 无
- 可并行: I-001

### I-003: 准备申请材料
- 为什么不可约分: 没有材料无法提交
- 移除测试: ❌ 无法跳过
- 依赖: I-001, I-002（需法规和确认结果）
- 可并行: 无

### I-004: 提交申请
- 为什么不可约分: 提交是注册的触发动作
- 移除测试: ❌ 无法跳过
- 依赖: I-003
- 可并行: 无

### I-005: 等待审核 + 处理补正
- 为什么不可约分: 审核是必经流程，不可控但不可跳过
- 移除测试: ❌ 无法跳过
- 依赖: I-004
- 可并行: 无
- 注意: 这是**外部等待环节**，不需要人主动做什么，但要留时间窗口
```

**不可约分环节类型模板**（按目标类型匹配）:

| 目标类型 | 典型不可约分环节 |
|---------|----------------|
| 注册/办证 | 查法规 → 确认口径 → 备材料 → 提交 → 等审核 → 领证 |
| 采购 | 需求确认 → 找供应商 → 比价 → 签合同 → 付款 → 验收 |
| 写作/创作 | 调研 → 大纲 → 初稿 → 修改 → 定稿 → 发布 |
| 调研 | 定范围 → 搜资料 → 整理 → 分析 → 出报告 |
| 部署/上线 | 环境准备 → 测试 → 部署 → 验证 → 监控 |
| 谈判/沟通 | 准备立场 → 首次接触 → 交换意见 → 达成共识 → 签署 |

### [3] task-decompose — 拆成 task 骨架

| 字段 | 内容 |
|------|------|
| **消费者** | [4] task-recipe（内部下游） |
| **产品** | `_internal/03-tasks-raw.md` |
| **Input** | `02-irreducibles.md` + `01-goal-parsed.md`（资源/约束） |
| **Output** | task 骨架列表：编号、标题、类型、依赖、预估时间、阻塞标记 |
| **工具** | `fs_read_file`，LLM 辅助估算时间 |
| **时间** | 10-15min |

**拆解规则**:
1. 每个不可约分环节 → 至少 1 个 task（可以拆成多个）
2. **外部等待环节**（如"等审核"）→ 1 个 task，时间 = 预估等待天数
3. **可以用工具/平台完成的** → 单独 task，标注所需工具
4. **必须人工的** → 单独 task，标注人员
5. 检查：去掉任何一个 task，目标还能完成吗？不能 → 保留

**Output 格式** (`03-tasks-raw.md`):

```markdown
# Task 骨架列表

## 总览
- 总 task 数: 7
- 关键路径长度: 5
- 可并行度: 2 对 (T-001∥T-002, T-006∥T-007)

## Tasks

### T-001
- 标题: 查阅《公司法》注册资本规定
- 类型: research
- 来源环节: I-001
- 预估时间: 45min
- 依赖: 无
- 阻塞项: 是
- 可并行: T-002

### T-002
- 标题: 联系工商局确认执行口径
- 类型: contact
- 来源环节: I-002
- 预估时间: 50min (30min电话 + 20min整理)
- 依赖: 无
- 阻塞项: 是
- 可并行: T-001
- 人员: 自己

### T-003
- 标题: 填写公司注册申请表
- 类型: fill-form
- 来源环节: I-003
- 预估时间: 60min
- 依赖: T-001, T-002
- 阻塞项: 否
- 可并行: 无
- 人员: 自己
- 工具: Excel/WPS

### T-004
- 标题: 提交注册申请
- 类型: submit
- 来源环节: I-004
- 预估时间: 30min
- 依赖: T-003
- 阻塞项: 否
- 可并行: 无
- 人员: 自己

- 阻塞项: 否 (被动等待)
- 可并行: 无
- 人员: 无

### T-006
- 标题: 处理审核补正（如需要）

### T-007
- 标题: 领取营业执照
- 类型: pickup
- 来源环节: I-005

- 依赖: T-005
```

### [4] task-recipe — 填充 8 字段菜谱

| 字段 | 内容 |
|------|------|
| **消费者** | [5/6/7] 后续组装 skill |
| **产品** | `_internal/04-recipes.md` |
| **Input** | `03-tasks-raw.md`（单个 task 骨架） |
| **Output** | 完整 8 字段 task: Input/Output/时间/资源/人员/前置/阻塞项/容错/完成标准 |
| **工具** | `fs_read_file`，LLM 辅助生成容错方案 |
| **时间** | 每个 task 3-5min，可并行处理多个 task |

**这是 Chef Bee 最核心的 skill——把骨架变成菜谱。** 每个 task 必须填满全部 9 个字段，不能留空。

**Output 格式** (`04-recipes.md`):

```markdown
# 完整 Task 菜谱

## T-001: 查阅《公司法》注册资本规定

| 字段 | 详细内容 |
|------|---------|
| **Input** | `01-goal-parsed.md` §法规约束, `https://www.gov.cn/` 国家法律法规数据库 |
| **Output** | `research/注册资本法规-2026.md` — 文件包含: (1)关键条款摘录≥3条 (2)每条标注发布日期 (3)适用性判断 (4)和当地工商局口径的对照空位 |
| **时间** | 45min |
| **资源** | 浏览器, 国家法律法规数据库 (gov.cn), 北大法宝 (备选) |
| **人员** | 自己 |
| **前置** | 无 |
| **阻塞项** | 是 — 不确定法规就没法填表(T-003)。如果阻塞: 后续 T-003/T-004 全部无法启动 |
| **容错** | 容错路径 A: 网站打不开 → 改用"微信搜一搜 公司法 注册资本 2024 最新" | 容错路径 B: 找不到确切条款 → 去知乎/小红书搜"公司注册 注册资本 经验",标注来源可信度 | 容错路径 C: 完全找不到 → 标记 `[需律师确认]`,先继续 T-002 从工商局窗口获取口径 |
| **完成标准** | (1)文件存在 (2)≥3条相关条款原文 (3)每条标注发布日期和来源 URL (4)有明确的使用建议 |

## T-002: 联系工商局确认执行口径

| 字段 | 详细内容 |
|------|---------|
| **Input** | T-001 产出 `research/注册资本法规-2026.md`, `01-goal-parsed.md` §人员约束 |
| **Output** | `research/窗口回复-20260701.md` — 文件包含: (1)通话时间 (2)联系人姓名/工号 (3)≥5条问答记录 (4)下一步操作指引 |
| **时间** | 50min (30min 电话 + 20min 整理) |
| **资源** | 电话, 录音(需告知对方), 笔记本 |
| **人员** | 自己 |
| **前置** | 无 (可与 T-001 并行) |
| **阻塞项** | 是 — 各地执行口径可能与法规不同。如果阻塞: T-003 填表时可能填错被退回 |
| **容错** | 容错路径 A: 电话打不通 → 发邮件到公示邮箱, 标注"等待回复(预计2工作日)", 先继续 T-001 | 容错路径 B: 对方说不清楚 → 问"那我应该找哪个部门",记录转介路径 | 容错路径 C: 完全联系不上 → 去小红书/知乎搜"XX市 公司注册 经验 2026",标注来源可信度"低",标记 `[待窗口确认]` |
| **完成标准** | (1)文件存在 (2)有联系人信息 (3)≥5条问答记录 (4)明确了材料清单是否有特殊要求 |

## T-003: 填写公司注册申请表

| 字段 | 详细内容 |
|------|---------|
| **Input** | T-001 产出 `research/注册资本法规-2026.md`, T-002 产出 `research/窗口回复-20260701.md`, `templates/注册申请表.xlsx` |
| **Output** | `output/注册申请表-已填写-v1.xlsx` — 所有必填字段已填写,不确定的有标注 |
| **时间** | 60min |
| **资源** | Excel/WPS, 身份证扫描件, 地址证明 |
| **人员** | 自己 |
| **前置** | T-001 DONE, T-002 DONE |
| **阻塞项** | 否 — 填完即可提交 T-004 |
| **容错** | 容错路径 A: 不确定的字段 → 标注 `[需确认: 待T-002回复]` | 容错路径 B: 表格下载不了 → 去政务服务网在线填 | 容错路径 C: 需要其他材料 → 在 T-002 的问答里补充询问 |
| **完成标准** | (1)文件存在 (2)所有必填字段已填写 (3)不确定项有 `[需确认]` 标注 (4)文件可被 Excel/WPS 正常打开 |
```

### [7] contingency-plan — 容错矩阵

```markdown
# 容错矩阵

## 阻塞风险热力图
| Task | 阻塞风险 | 说明 |
|------|---------|------|
| T-001 | 🟡 中 | 网站可能打不开，有 3 条容错路径 |
| T-002 | 🔴 高 | 电话可能打不通，回复可能慢，影响后续所有 |
| T-003 | 🟢 低 | 不依赖外部，纯填写 |
| T-004 | 🟢 低 | 在线提交，失败重试即可 |
| T-005 | 🟡 中 | 外部等待不可控，但不需要人主动做什么 |
| T-006 | 🟢 低 | 条件触发，不一定需要 |

## 升级路径（容错全失败时的处理）
| 场景 | 容错路径全部走完仍失败 | 升级动作 |
|------|---------------------|---------|
| T-001 完全找不到法规 | 3条路径都失败 | → 解锁 PLAN，替换为"委托代理公司办理"方案 |
| T-002 完全联系不上 | 3条路径都失败 | → 解锁 PLAN，用低可信度信息先填表，标注风险 |
| T-005 审核被拒 | 补正后仍被拒 | → 解锁 PLAN，分析拒绝原因，重新生成计划 |

## PLAN 解锁条件
以下条件任一满足时，PLAN.lock 自动释放（由 Verification Bee 检测）:
1. 任一"高"阻塞风险 task 的容错路径全部走完仍失败
2. 外部新信息（法规变更、窗口回复否定、预算被砍）
3. T-005 审核返回"拒绝"（非"补正"）
```

### [9] plan-lock — 决策锁

| 字段 | 内容 |
|------|------|

## 四、角色二：交付触发器 — 3 个 skill

### 消费者：创作者（正在做事的 Worker Bee 或人）
### 产品：交付决策（"发" or "改"）

```
当前版本 v_N
    │
    ▼
[10] diff-check     → delivery/diffs/vN-vN-1.diff    （边际收益探测）
    │
    ▼
[11] delivery-decide → 交付决策（"发" or "改"）       （交付决策）
    │
    │ 如果"发" → delivered
    │   └─ 等待外部反馈
    │       ├─ 收到反馈 → done（关闭）或 新 backlog
    │       └─ 没回 → [12] follow-up（追回）
    │
    │ 如果"改" → 继续迭代
```

### [10] diff-check — 边际收益探测

| 字段 | 内容 |
|------|------|
| **消费者** | [11] delivery-decide |
| **产品** | `delivery/diffs/<task>-vN-vN-1.diff` |
| **Input** | 当前版本文件 + 上一版本文件 |
| **Output** | diff 统计：变更行数，有效变更行数（排除格式/空白），是否趋零 |
| **工具** | `sys_terminal` (diff 命令) |
| **时间** | 1min |

**diff 判别规则**:
```python
有效变更行 = 总变更行 - 空白行变更 - 仅格式变更行
if 有效变更行 < 总行数 * 0.05:  # 变更 < 5%
    return "趋零"
elif 修改轮次 >= 3 and 有效变更行 < 总行数 * 0.10:  # 第3轮后 < 10%
    return "趋零"
else:
    return "仍有实质变化"
```

**Output 格式** (`delivery/diffs/<task>-v3-v2.diff`):
```
# Diff: T-003 申请表 v2 → v3
- 总变更行: 5
- 有效变更行: 2 (3行是空白调整)
- 总行数: 45
- 变更比例: 4.4%
- 状态: ⚠️ 趋零 — 边际收益已很低
- 修改轮次: 3
```

### [11] delivery-decide — 交付决策

| 字段 | 内容 |
|------|------|
| **消费者** | 创作者 |
| **产品** | 交付决策 |
| **Input** | diff 结果 + 修改轮次 + 是否收到过外部反馈 |
| **Output** | "发" or "改" + 理由 |
| **工具** | `fs_read_file`（读 diff） |
| **时间** | 1min |

**决策规则**（纯规则，不调 LLM）:

| 条件 | 决策 | 理由 |
|------|------|------|
| diff 趋零 + 轮次 ≥ 3 + 无外部反馈 | **发** | 内部迭代边际收益为零，需要外部信息 |
| diff 趋零 + 轮次 ≥ 1 + 用户说"差不多" | **发** | 用户主观认为够了 |
| diff 仍有实质变化 + 轮次 < 3 | **改** | 每次改还有明显进步 |
| 外部反馈已收到 + 已按反馈修改 | **发** | 不要追加新修改 |
| 用户说"再改一轮" + diff 已趋零 | **追问后发** | "哪里还要改？说不出来就发" |

**决策记录写入** `delivery/state.json`:
```json
{
  "T-003": {
    "status": "delivered",
    "delivered_at": "2026-07-01T15:30:00Z",
    "version": "v3",
    "rounds": 3,
    "decision": "发 — 内部迭代边际收益趋零 (4.4%)",
    "waiting_feedback_from": "工商局窗口",
    "follow_up_at": "2026-07-04T09:00:00Z"
  }
}
```

## 六、Chef Bee 与 Commander Bee 的接口

Chef Bee 不直接和 Worker Bee 通信。它产出的 `PLAN.md` 交给 Commander Bee，由 Commander 做最后的拆解和派发。

```
Chef Bee                     Commander Bee
  │                              │
  ├─ PLAN.md 写入                │
  ├─ PLAN.lock 锁定              │
  │                              │
  └──────────┬───────────────────│
             │ 读取 PLAN.md      │
             │                   │
             ▼                   │
       Commander Bee             │
             │                   │
     task-decompose (Commander)  │  ← 把 PLAN.md 里的 task 转成 Job Board 的 Job
             │                   │
     task-dispatch (Commander)   │  ← 匹配 Worker + Deck
             │                   │
             ▼                   │
         Job Board               │
             │                   │
             ▼                   │
        Worker Bee               │
```

**接口契约**: PLAN.md 的每个 task 包含 Commander 拆 Job 所需的全部信息（类型、时间、依赖、人员），Commander 不重新分析，只做格式转换。

---

## 七、Chef Bee 与 Verification Bee 的接口

Verification Bee 在执行阶段监控：
1. 读取 `state.json` → 检查哪些 task 在 doing 状态
2. 读取 `07-contingency.md` → 知道什么条件触发解锁
3. 检测到解锁条件 → 写入 `pheromones/warnings/PLAN-unlock-<project>.md`
4. Chef Bee（或人）看到 warning → 决定是否解锁 PLAN

## 九、设计原则

1. **消费者驱动设计** — 每个 skill 先定义"谁用这个产出"，再定义怎么产
2. **文件接力** — skill 之间不传内存对象，只传文件。每个中间产物可被人中断、检查、修改
3. **纯规则优先** — 能用规则就不用 LLM。LLM 只用在需要"创意"的地方（容错方案）
4. **过饱和展开** — 中间产物不删，全部保留在 `_internal/`，审计和回溯随时可用
5. **决策锁边界清晰** — 锁的是"计划是否要重做"，不是"task 是否可以调整"
