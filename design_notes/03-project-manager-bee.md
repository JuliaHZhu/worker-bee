# Project Manager Bee — 行动计划生成器 + 交付触发器

> *从头脑风暴到菜谱级执行方案。先过饱和，再执行。*

## PM Bee 的双重角色

| 角色 | 做什么 | 阶段 |
|------|--------|------|
| **行动计划生成器** | 从行动目标文件生成菜谱级任务计划 | 启动阶段 |
| **交付触发器** | 探测边际收益拐点，强制交付 | 执行阶段 |

这是同一个 PM Bee 的两个面——先在启动时把计划"过饱和"地展开，再在执行中管节奏。

---

## 角色一：行动计划生成器

### 输入

一个头脑风暴文件（`GOAL.md`），包含：
- 行动目标（我要做什么）
- 已有线索/想法
- 已知约束（时间/资源/人/法规/平台）
- 不确定项

### 核心原则

1. **不可约分环节优先** — 先列出"不做就完蛋"的最小必需步骤，不跳过
2. **过饱和展开** — 信息宁可冗余，不要在执行时缺。不在展开阶段用奥卡姆剃刀
3. **菜谱级精确** — 每个 task 像烤蛋糕配方：input 精确到文件路径，output 精确到交付物格式，时间估算精确到分钟
4. **容错内置** — 每个环节预设 fallback 方案和阻塞处理路径
5. **文件锁 = 决策锁** — 行动计划写入后上锁，执行阶段只执行不讨论

### 输出格式：行动计划（`PLAN.md`）

```markdown
# 行动计划: <目标名称>

## Meta
- 源文件: GOAL.md
- 生成时间: 2026-07-01T10:00:00Z
- 总预估时间: 14h
- 状态: LOCKED  ← 文件锁，表示已决策，执行阶段不讨论

## Resource Pool
- 人员: [自己], [可联系的外部人A], [可联系的外部人B]
- 资金: ￥X
- 工具: [工具1], [工具2]
- 平台: [平台名]

## Task Dependency Graph
```
T-001 (查阅法规) ──┬── T-003 (填写表格A)
                   │
T-002 (联系窗口) ──┘
                   │
                   └── T-004 (提交审核) ── T-005 (等结果) ──┬── T-006 (补充材料)
                                                           │
                                                           └── T-007 (领取结果)
```

## Tasks

### T-001: 查阅《公司法》关于注册资本的最新规定

| 字段 | 内容 |
|------|------|
| **Input** | GOAL.md §约束, 国家企业信用信息公示系统 URL |
| **Output** | `research/注册资本法规.md` — 关键条款摘录 + 适用性判断 |
| **时间** | 45min |
| **资源** | 浏览器, 国家法律法规数据库 |
| **前置** | 无 |
| **阻塞项** | 是 — 不确定法规就没法填表 |
| **容错** | 如果网站打不开 → 改用微信搜一搜"公司法 注册资本 2024" |
| **完成标准** | 文件包含 ≥3 条相关条款，每条标注发布日期和适用范围 |

### T-002: 联系工商局确认当地执行口径

| 字段 | 内容 |
|------|------|
| **Input** | T-001 的输出（法规摘要），GOAL.md §联系人 |
| **Output** | `research/窗口回复.md` — 记录联系人、时间、答复要点 |
| **时间** | 30min（电话）+ 20min（整理） |
| **资源** | 电话 |
| **前置** | 无（可与 T-001 并行） |
| **阻塞项** | 是 — 各地执行口径可能和法规不同 |
| **容错** | 电话打不通 → 发邮件，标注"等待回复 (预计2工作日)"，先继续 T-003 |
| **完成标准** | 文件包含: 联系人姓名, 通话时间, ≥3 条答复要点 |

### T-003: 填写公司注册申请表

| 字段 | 内容 |
|------|------|
| **Input** | T-001 的法规摘要, T-002 的窗口回复, `templates/注册申请表.xlsx` |
| **Output** | `output/注册申请表-已填写.xlsx` |
| **时间** | 60min |
| **资源** | Excel/WPS |
| **前置** | T-001 DONE, T-002 DONE |
| **阻塞项** | 否 — 填完即可提交 |
| **容错** | 不确定的字段标注 `[需确认]`，附注"待 T-002 回复后补充" |
| **完成标准** | 所有必填字段已填写，不确定项有标注 |
```

### Task 字段规范

| 字段 | 要求 | 示例 |
|------|------|------|
| **Input** | 精确到文件路径或 URL，不要模糊的"相关资料" | `research/法规.md` |
| **Output** | 精确到文件名和格式，含存放路径 | `output/申请表-已填.xlsx` |
| **时间** | 精确到分钟，不含"左右""大约" | `45min` |
| **资源** | 列出具体工具/平台名称 | `WPS, 国家企业信用信息公示系统` |
| **前置** | 明确标注依赖关系，用 T-xxx 编号 | `T-001 DONE, T-002 DONE` |
| **阻塞项** | 是/否 + 为什么 | `是 — 不确定法规就没法填表` |
| **容错** | 至少一个可操作的 fallback，不要"等待" | `网站打不开 → 改用微信搜一搜` |
| **完成标准** | 可验证的条件，不用主观词 | `≥3条条款，每条标注日期` |

## 角色二：交付触发器（保留原有逻辑）

### 不管质量。只管节奏。

| 信号 | PM Bee 行为 |
|------|-----------|
| "改了三版了" | 检查 diff 是否趋零 → 提醒交付 |
| "差不多吧" | 追问：哪里还觉得不够？说不出来 → 交付 |
| "要不要再改一轮" | 追问：新信息从哪来？没有 → 交付 |
| "发了没回" | 设追的轮次（3天/5天），主动推进 |

状态机不变：`backlog → ready → doing → delivered → done`

Done 不是内部决定的——done 是外部告诉你才算的。

## 决策锁机制

行动计划生成后，`PLAN.md` 写入并设置文件锁：

```python
import fcntl
lockfile = open("PLAN.lock", "w")
fcntl.flock(lockfile, fcntl.LOCK_EX | fcntl.LOCK_NB)
```

- **锁定后**：执行阶段只执行 task，不讨论"这个 task 有没有必要"
- **解锁条件**：外部新信息（法规变了、窗口回复和预期不同、预算被砍）或 task 容错路径全部走完仍然阻塞
- **锁不是不可变的**：它是"决策已完成"的信号，不是"永不修改"的枷锁。但修改需要明确的触发条件

## 与 Architecture Bee / Aristotle Bee 的分工

| | Architecture Bee | PM Bee |
|---|---|---|
| 管什么 | 系统怎么设计 | 事情怎么执行 |
| 输入 | 需求/约束/技术选型 | GOAL.md（头脑风暴） |
| 输出 | 架构骨架 | 菜谱级任务计划 |
| 精度 | 模块级别 | 文件级别 |
| 容错 | 备选架构 | 每个 task 的 fallback |

## 外源信息素格式

### 行动计划文件
**路径**: `~/.worker-bee/pm/<project>/PLAN.md`
**格式**: 见上方 Task 字段规范

### 头脑风暴文件
**路径**: `~/.worker-bee/pm/<project>/GOAL.md`
**格式**: 自由格式 markdown

### 决策锁
**路径**: `~/.worker-bee/pm/<project>/PLAN.lock`
**格式**: fcntl 排他锁
